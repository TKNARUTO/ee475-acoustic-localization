# 延迟优化结果：RX2

日期：2026-10-27 · Pico 固件 0.6-RX2

根据前一阶段报告，这次处理正常循环中的设备与音频传输等待。**实测整包接收和校验从约 208 ms 降到 164 ms，减少约 21%；实际界面检测刷新约每秒 5.35 次。** 新固件已经加载到当前 Pico，程序也已更新并打开，扫描关闭。

## 1. 找到的耗时与对应修改

先在固件里补计时，再依次测试 USB 缓冲调整、CRC 加速。设备端计时确认：原来的逐位 CRC 每包要约 22.47 ms；原来的小 USB 缓冲发送 57,344 字节负载约要 101.78 ms。这和前一份报告中电脑 CRC 约 0.04 ms 并不矛盾，是不同处理环节。

| 中位数 | 仪表化旧配置 | RX2 最终配置 |
| --- | ---: | ---: |
| Pico CRC | 22.47 ms | 7.17 ms |
| Pico 负载发送 | 101.78 ms | 70.42 ms |
| 主机请求到整包校验完成 | 208.42 ms | 164.48 ms |
| 主机请求到结果入队 | 222.67 ms | 176.61 ms |
| 相邻请求间隔 | 236.19 ms | 189.01 ms |
| 采集/估计频率 | 4.23 Hz | 5.29 Hz |

表中每个配置均采集 100 包环境声，采样格式相同；正常包指标排除 ≥450 ms 的启动周期。后续自动更新验证再次收到 100 包，整包中位数 164.10 ms，与最终配置相符。部分探索测试期间同时进行了编译，主机精确数值会受负载影响；这些数字用于说明正常数据链路的改善，不是手机定位角度实验。

USB 软件发送 FIFO 改为 4096 字节，接收 FIFO 和端点传输缓冲为 512 字节；USB 全速端点的数据包大小仍是 64 字节。CRC 改用 256 项查表，算法规则保持不变，没有跳过校验。

另测了 1024 字节传输缓冲，整包约 163.09 ms，相比 512 字节的改善只有约 1.4 ms，所以保留内存占用较小的 512 字节配置。

## 2. 界面实际结果

20 秒实际 GUI/Pico 检查接收了 91 包，21 项检查全部通过。七路采集、扫描开关、导入、频谱、波形、窗口布局均正常，没有回调错误。

| 当前界面测试指标 | 中位数 | P95 |
| --- | ---: | ---: |
| 请求到整包校验完成 | 158.61 ms | 172.78 ms |
| 请求到绘图指令完成 | 194.15 ms | 218.13 ms |
| 结果入队到绘图指令完成 | 20.90 ms | 39.16 ms |

界面刷新约 32.26 Hz，检测更新约 5.35 Hz。这里“绘图完成”是 Tk 绘图命令完成，不是显示器实际出帧。不同 GUI 操作和 DMA 块对齐会使该轮中位数与单独采集测试略有不同；不要把各项独立中位数直接相加。

4096 点／48 kHz 的窗口本身仍是 85.33 ms，首次或恢复后仍有 500 ms 预热。这次不缩短音频、降低采样率，也不改变既有确认、历史窗口和平滑。所以从手机开始播放到稳定正确箭头的总延迟，还需要实际播放测试，不能直接称为 164 ms 或 194 ms。

## 3. 校验和恢复是否仍然可用

实际 Pico 的三个 CRC 向量与独立的 Python zlib 结果一致：标准字符串 CBF43926、空输入 00000000、00–FF 字节序列 29058C73。正常测试包仍逐包检查长度、CRC 和序号结尾，记录的 dropped 和 RX stall 均为 0。

保留 RX1 恢复流程，又做了一次实际故障注入：一包改坏一位数据、一包模拟接收停顿，两包均被拒绝，随后自动恢复。这轮收到 46 个好包；从检出异常到下一包完整数据，分别约 700 ms 和 1,151 ms，不包含检出异常前的等待。

旧版 v0.5 自动更新到 v0.6 的流程也已验证，随后收到 100 个完整包。默认 UF2 和配套 ELF 来自同一构建。所有加载均先检查 SRAM 地址范围，Flash 负载块为 0。

开发中第一次 USB 配置只放大了发送及传输缓冲，没有联动接收 FIFO，导致无法接收命令。已根据 TinyUSB 接收条件修正并重新测试。该失败配置仅保留为开发证据，不是默认固件，也不能用它解释历史 v0.5 的偶发坏包。

## 4. 还没有解决的部分

这次降低的是正常数据链路等待。定位算法、通道顺序、几何配置、平滑、两次候选确认和界面代码均未改，没有加回大角度转向限制。`group_delay_inconsistent` 是麦克风间相对时差拟合问题，和每包传输花多少毫秒需要分别验收。

本次没有新的手机信标实录，因此不能说反向跳变、时差不一致、远距离识别或高频灵敏度已经改善。你方便时，用原来的 `01_LOCATE_20kHz_19-21kHz.mp3` 播放测试；先固定在约 0.5 m，Advanced → 输入距离 → Record 10 s。记录手机在阵列哪一侧后，就能继续分析原始七路数据。
