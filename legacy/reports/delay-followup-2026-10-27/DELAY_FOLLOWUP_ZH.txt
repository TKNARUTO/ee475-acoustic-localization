# 延迟排查后续：收包恢复阶段

日期：2026-10-27 · 阶段 RX1 · Pico 固件 v0.5

本次已经完成电脑端收包流程改进，并用接着的 Pico 验证了异常恢复。它解决的是“坏包后整段停好几秒”的恢复问题；20 kHz 下经常报时差不一致、偶发反向的问题仍待手机原始数据分析。用户本次不方便播放手机信标，定位测试留到下一阶段。

## 一、现在能把延迟分到哪些环节

以前 `capture_cycle_ms` 把采集、接收和计算合在一起。这次用高精度计时，分别记录发命令、包头、音频、校验、DSP 和界面绘制。先后做了 145 包粗计时、103 包高精度基线和 72 包实际界面检查；正常接收均没有新的完整性错误。它们都是环境声数据，不能算手机信标定位验收。

实际界面测试的统计如下：

| 环节 | 中位数 | P95 | 含义 |
| --- | ---: | ---: | --- |
| 发出 RECORD 后到包头完整 | 104.27 ms | 114.14 ms | 含设备采集、调度、固件工作和包头到达 |
| 包头完整到音频读完 | 99.36 ms | 102.57 ms | 主机可见的负载接收段 |
| 电脑 CRC 计算 | 0.043 ms | 0.071 ms | 不是主要耗时 |
| 请求到整包校验完成 | 201.56 ms | 215.72 ms | 正常包，排除 ≥450 ms 启动周期 |
| DSP 估计 | 4.33 ms | 6.63 ms | 本次环境声；不能替代强信标计算耗时 |
| 结果入队到绘图指令完成 | 19.95 ms | 45.86 ms | GUI 等待和本轮绘制工作 |
| 请求到绘图指令完成 | 236.29 ms | 265.19 ms | 不是手机发声到正确箭头的端到端延迟 |

界面观测刷新约 32.26 Hz，采集/估计约 4.57 Hz。包头前约 104 ms 与负载接收约 99 ms 是目前正常循环的主要两段。4096 点、48 kHz 的音频窗口本身需要 85.33 ms；首次或恢复后的采集仍有 500 ms 固件预热。还没有设备内部边界时间戳，不能继续把包头前的剩余时间拆成精确的 CRC、DMA 对齐或 USB 调度耗时。

绘图指令完成表示 Tk 已调用画图命令，不表示量过显示器实际出帧。确认次数、历史窗口、平滑和方向拒绝对最终箭头的影响，也没有包含在“236 ms”这个结论里。此次正常循环延迟没有被证明明显降低。

高精度基线为 103 包，正常包请求到校验完成中位数 207.22 ms。它和界面测试的运行条件不同，不能用两者约 6 ms 的差值宣称提速。

## 二、对长停顿做了什么

旧程序把“短包”和“CRC 不符”合并报错，然后退出串口会话、固定等 3 秒重连。历史日志中有两次约 8.5 秒没有新结果。新的处理顺序是：

1. 确认错误种类，记录序号、实际/期望字节数、可用 CRC 和分段耗时；坏数据不进入定位。
2. 发 STOP，一边清掉残留数据，一边等 Pico 的明确停止回复。每 200 ms 可重发一次，整个恢复最多等 1.2 秒。
3. 收到确认后重新采集，清掉旧定位历史。单次可恢复故障不再经过固定 3 秒重连等待。
4. 如果无法重新对齐、连续三次收包故障，或串口本身不可用，仍走原有重连流程。

负载连续 600 ms 没进展会判作短包，另保留 4 秒总截止时间。单次读取使用 20 ms 超时并累积碎片，不把一次短读误判为整包结束。停止/换模式产生的取消单独记为 `PACKET_CANCEL`。

## 三、真实 Pico 的故障注入结果

使用当前 v0.5 RAM 固件，故障只注入在电脑读取的数据上，没有改写固件或播放测试音。

| 注入故障 | 程序识别结果 | 检出错误到下一包完整数据 |
| --- | --- | ---: |
| 电脑端改动一位负载数据 | CRC 不匹配，拒绝该包，原串口内恢复 | 737 ms |
| 暂停主机读取一包负载 | 短包，拒绝该包，原串口内恢复 | 1,188 ms |

这轮接收了 36 个好包，两次坏包均被拒绝，没有退出会话进入外层 ERROR 重连。上述时间包含重启后的预热，**不包含检测故障前已经等待的时间**。停顿注入中，检出短包前约等了 610 ms；因此不能把 1,188 ms 当成整个故障持续时间。

第一次试验还发现：只发一次 STOP，在模拟接收停顿后可能等不到确认。修订后在排空数据期间有限重试，第二次试验两种故障均通过。第一次失败日志也已保留。

这些试验验证了新恢复流程，但没有证明历史两次错误也是同一个原因，更不代表所有 USB 异常都能在这些时间内恢复。

## 四、与方向问题的关系

此前已定位：频繁的 `group_delay_inconsistent` 通常发生在音频完整到达、编码已识别之后，是多麦克风相对时差无法共同满足几何模型。收包恢复与这件事需要分别验收。

本次 `highband_dsp.py`、几何配置、定位门槛、两次候选确认、音频和固件均未改；没有加回大角度转向限制或双估计硬拦截。不能把无效方向改成有效方向来当作修复，也不能用 Set Front 或强制翻转来解释手机固定时突然反指。

下一步需要新的 20 kHz 原始波形。保持手机固定、记录约 0.5 m 测试，检查每对麦克风的时差是否闭合、中心通道是否有系统偏差、各路频响是否不同以及反射路径是否混入。得到实录后，再改一个定位环节并重放验证。
