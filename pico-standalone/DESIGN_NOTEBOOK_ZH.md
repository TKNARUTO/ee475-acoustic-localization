## 1 我理解的任务

你要的是：手机播放现有 HF2 Gap 信标，SEN0325 收音，**Pico 自己识别信标并算出方向**，再把方向交给 ESP32。拔掉电脑后，只要板子还有独立供电，定位和串口输出就应继续。电脑只保留监控、校准与调试用途。

这与上一版“电脑计算后，经 Pico 转给 ESP32”不同。上一版桥接代码已保存，但没有部署，不能用它证明独立定位。

本阶段交付范围是独立定位原型和通信验证。暂不编写电机驱动、距离控制、避障或完整跟随逻辑。你提出的 control loop 作为后续集成目标；本阶段先测出定位的内存和执行时间，才有依据分配控制周期。

需要保留的约束：

- 继续用现有 `HF2-gap-test` 音频，18–22 kHz、48 kHz 采样；不偷偷替换手机音频。
- 不依据上一帧方向强行禁止大角度转向。
- 不改变已接好的阵列线路；Pico GP0 接 ESP32 P16，GP1 接 P17，共地。
- 先分阶段验证，再更新实际运行版本；原工作版本可恢复。
- 这版 C 原型先固定识别项目的 HF2 Gap 信标。手机播放器仍可导入其他文件，但**导入播放不等于 Pico 已支持该文件的定位**。可配置模板是后续接口工作。

```mermaid
flowchart LR
  Phone[手机 HF2 Gap 音频] -->|声波| Mic[SEN0325 七麦]
  Mic -->|同步 I2S| Capture[Pico PIO DMA 采集]
```

## 3 信号和几何依据

已有代码和音频文件确认：一个周期为 4096 点，前 2048 点是编码声，后 2048 点静音。

| 计算 | 结果 | 用途 |
|---|---:|---|
| 4096 / 48000 | 85.333 ms | 一个分析窗覆盖一个完整信标周期 |
| 2048 / 48000 | 42.667 ms | 每段发声、静音的时间 |
| 4096 × 7 × 2 | 57,344 B，56 KiB | 七路 PCM16 缓存 |
| 0.04 / 343 × 48000 | 5.598 点 | 水平入射时，中心到外圈的最大理论时差 |
| 0.08 / 343 × 48000 | 11.195 点 | 直径两端麦克风的最大理论时差 |

半径 40 mm、声速 343 m/s 来自现有几何配置；真实安装方向和通道误差仍需校准。声源高度也会改变二维投影长度，不能把所有偏差都归因于程序。

通道顺序固定为 D0L、D0R、D1L、D1R、D2L、D2R、D3R_CENTER。原始角度 0° 对应阵列 U7/M0 参考，顺时针增加。电脑的 Set Front 偏置不会自动成为机器人车头偏置。

**容易翻转方向的符号：** 声源靠近某麦时，该麦先收到信号，匹配峰的采样位置更早。到达时间差满足 `arrival_i - arrival_j = -(Fs/c) × (position_i-position_j)·direction`。C 的到达时间拟合必须保留这个负号；不能直接照搬相位斜率公式的符号。

## 4 为什么先选匹配包络和到达时间拟合

本次选择是移植现有算法中的“指定码匹配 → 多麦候选到达峰 → 几何一致性拟合”。第一步暂不移植电脑上较大的谱延迟搜索表和联合方向搜索。

最初选型证据：11 月 5 日，两份真实录音共 40 窗的只读回放中，Python 的 arrival-only 路径与完整路径有效/无效判定相同；共同有效角度最大差约 6.95°。录音中手机在移动，没有已知真角度，不能证明物理准确度。后续 C 与 Python arrival 对照已完成，结果见第 9 节；板上速度另见第 11 节。

处理过程：

1. 检查采集是否丢块、是否削顶；不把损坏窗口送去控制。
2. 七路麦克风依次做 FFT，与同一 HF2 Gap 模板相关；复用工作区。
3. 对窄频尖峰做有上限的频谱白化，避免一个电子啸叫主导匹配。它不是提高麦克风的物理灵敏度。
4. 按现有 PNR 与带内 RMS 条件判断信标。至少四麦表示码命中；当前 arrival-only 路径要求至少六麦命中才进入拟合，最终至少保留五麦。四到五麦命中仍可能没有方向，这是移植该子路径的能力边界。
5. 在同一到达事件附近选择真实局部峰，拟合二维方向和共同到达时间；允许一次有限的异常麦剔除。
6. 依据本窗口证据给出几何有效性、原始角度和质量；不比较上一个方向来限制转向。调用层还要求两次码命中，窗口中心间隔小于 750 ms；最终 UART valid 同时要求几何有效、已确认、未过期。USB 分别报告 fit_valid、confirmed 和 valid，避免混淆拒绝原因。

未选的定位路线：直接比较各麦分贝容易被扬声器朝向和反射误导；只用 20 kHz 载波相位容易存在空间多解；直接搬 Python/NumPy 全部中间数组会超过内存预算。后续已验证整数 FFT 和 FAST 算术优化，保留 float 可回退版本；未降采样、未改频带。更多优化目前暂停。

## 5 内存账目与算力边界

以下是旧 ELF 的链接结果，不是实时内存测量。Pico 总 SRAM 为 264 KiB，其中默认主 RAM 区是 256 KiB，另有两个 4 KiB 区域。

| 主 RAM 项目 | 已验证 v0.6 采集固件 | 未部署 v0.8 桥接固件 |
|---|---:|---:|
| 加载到 RAM 的代码、常量、初始化数据 | 109,416 B | 114,040 B |
| BSS，包括音频缓存 | 138,104 B | 140,472 B |
| 主 RAM 固定占用 | 247,520 B | 254,512 B |
| 主 RAM 剩余 heap 区上限 | 14,624 B | 7,632 B |

v0.8 另在独立区域预留 4096 B core0 栈。不能把 ELF `size` 的所有 text 数字都当成可执行代码，也不能把 heap 区上限当成运行时空闲内存。

本次分配：DMA 块由 1024 帧缩至 512 帧，双缓冲从 64 KiB 减到 32 KiB；4096×7 PCM 仍为 56 KiB。DSP 静态工作区目标不超过 56 KiB。代码和常量准备采用 Flash XIP，RAM 候选用于可恢复测试；最后以新 ELF/map 实际结果为准，不能把估算剩余空间当成已兑现余量。

当前时钟设置为 120 MHz，只使用 core0。core1 空着不等于完整定位一定有实时余量。旧 `process_us` 只覆盖某次块处理，不含 CRC、USB 等全部工作，不能据此宣称“CPU 只用了某个百分比”。

## 6 调度与以后加入 control loop

第一阶段采用易核查的顺序原型：新窗口采集 → 定位计算 → 输出 → 下一新窗口。它不宣称连续无间隙采样。USB 只在缓冲有空间时发送短诊断，电脑不读取时也要继续；原来的整窗 USB 写入不能阻塞自主定位。

两个周期要分别测量：

- **新方向周期**：音频窗时间、DSP 时间和调度间隔共同决定。
- **控制周期**：例如未来每 10–20 ms 更新一次转向控制，这只是候选设计频率，不是本次已实现指标。

简单 PID 的状态量很少，但固定周期不能建立在一个会阻塞数十毫秒或更久的主循环尾部。先测 DSP 最坏时间，再决定用独立定时任务还是 core1；后续还要接真实速度/距离反馈。更快重复读取旧角度，不会产生更多新方向信息。

## 7 Pico 与 ESP32 的数据约定

三线 UART：GP0/TX → ESP P16/RX；GP1/RX ← ESP P17/TX；GND 共地，115200 8N1，3.3 V 逻辑。两板各自 USB 供电，不连接板间 3V3/5V/VIN。

沿用接收固件的 H/B/ACK 协议：启动时换新会话，测量序号递增，CRC16 检错，包含 valid、角度、质量和测量年龄。质量是工程分数，不是正确概率；invalid 不是“正前方 0°”。

年龄计划从窗口中心算到真正发送时刻，约含半窗 42.67 ms 和 DSP 时间。ESP32 的有效期为 500 ms，并计入 20 ms 通信预算。若计算太慢而被判过期，应优化并报告真实速度，不能填 age=0 或偷偷放宽阈值。USB 显示延迟与 UART 接收年龄要分别记录。

## 8 预期故障和检查办法

| 现象 | 需要排查的原因 | 检查办法 |
|---|---|---|
| 总体翻转 180° | 到达差符号、麦克风顺序 | 全圆合成测试，再做已知真角度实测 |
| 整体偏转固定角度 | 阵列参考与车头参考不同 | 单独保存车头标定，不改算法符号掩盖问题 |
| 跳向反射方向 | 多径峰选择、弱信号 | 保存本窗口峰与拟合残差，不锁死大转向 |
| 没有信标也出箭头 | 检测过松、错码碰撞 | 静音、背景、纯音和错误编码分别测试 |
| 接电脑能跑，拔电脑停 | 等待 USB、依赖 PC 命令 | 用独立电源启动，ESP32 观察持续包序号 |
| 角度算出但 ESP 判旧 | 计算耗时大、年龄边界错误 | 记录 capture_us、dsp_us、age_ms、ACK status |
| Pico 重启后 ESP 拒包 | 重用了旧 session，序号归零 | 重启测试并核对会话变更 |
| 偶发数据坏或死机 | DMA 覆写、栈溢出、队列溢出 | 所有权检查、丢块计数、栈/内存界限与持续测试 |

### 已测版本，不能混淆测试条件

| 候选 | 条件 | DSP中位数 | 结果间隔/周期 | 测量年龄 |
|---|---|---:|---:|---:|
| float RAM | 5窗，未检出信标 | 2734 ms | 约2827 ms | 约2779 ms |
| integer RAM | 13窗，未检出信标 | 1040 ms | 约1131 ms | 1085 ms |
| integer FAST RAM | 17窗，用户正在试播 | 792 ms | 周期中位数885 ms | 837 ms |

有信标时会增加包络归一化和候选提取工作，不能直接把不同信号条件的总耗时差全算成优化收益。FAST输入/输出转换和整数运算的严格测试：580窗整个结果结构逐字节一致；实际FFT边界转换各66,519,040个值一致。此前整数与float的580窗有效性判定一致，最大角差0.036026°；这不是物理误差保证。

FAST试播17窗中，16窗七麦码命中、1窗只有一麦命中；7窗有几何拟合，9窗时差不一致，1窗未检出信标。最终valid均为0：计算仍晚于500ms接口预算，连续窗口间隔也超过750ms确认条件。监控显示的橙色诊断拟合不能用于控制；没有将年龄置零或放宽过期门限。

同17窗的平均一轮881.24ms：FFT/逆FFT451.95ms，包络峰提取188.05ms，白化/匹配100.35ms，DSP之外采集/调度93.08ms，其他DSP42.20ms，最后几何拟合5.61ms。解包14.59ms与采集过程重叠，不能再次相加。把最后拟合移到ESP32最多省很小一部分，不是本轮主要优化路线。

算力表述：目前core0为120MHz，core1未使用。DSP+解包的计时约占周期91%，这只是已计时工作段占比，不是精确总CPU使用率，也不代表能在主循环尾部准时运行控制环。旧版电脑估计的4–16ms不能拿来当Pico运算能力。

后续白化/缓存候选 W1C1 已完成 580 窗离线对照：valid/reason/code_channels 无差异，最大角差约 0.000732°；只构建，未上板。双核仅有按麦克风分工的设计，没有实现。用户现已暂停这两条优化路线，优先通信；不得把预计加速写成实测。恢复双核时需重新报告每核时间、同步等待、内存和栈余量。仍不屏蔽大角度、不改音频、频带、采样率或 PNR 门限。

### 多项目合并的带宽预算

以下按当前源码和线格式计算，不是逻辑分析仪量测。MB/kB使用十进制；KiB使用1024字节。

| 接口/数据 | 当前预算 | 含义 |
|---|---:|---|
| I2S每根数据线 | 48,000 × 2时隙 × 32位 = 3.072 Mbit/s | 四根数据线共用BCLK 3.072MHz、WS 48kHz |
| 四线合计 | 12.288 Mbit/s | 包含时隙填充和未使用的第八声道，不是单线12.288MHz |
| PIO状态机时钟 | 128 × 48,000 = 6.144MHz | 两个PIO周期对应一个I2S位时钟 |
| DMA写入原始缓存 | 8个32位word/帧 × 48,000 = 1.536 MB/s | 即使DSP在忙，DMA仍继续循环采集；该阶段窗口被跳过 |
| 七路有效24位信号 | 7 × 24 × 48,000 = 8.064 Mbit/s | 仅有效位，不含I2S填充 |
| 解包PCM16 | 7 × 2 × 48,000 = 672 kB/s | 连续解包的理论数据量；当前只处理选中窗口 |
| 每个PCM分析窗 | 4096 × 7 × 2 = 57,344 B = 56KiB | 不等于每秒传这么多 |
| 一个DMA块 | 512 × 8 × 4 = 16KiB，每10.667ms完成 | 双缓冲共32KiB，完成块必须在另一块填满前处理 |
| 方向B包 | 最多49字节，115200 8N1约4.25ms在线时间 | 每秒5包占发送方向约2.13%；不是总声学延迟 |
| 回执ACK | 最多45字节，约3.91ms在线时间 | 全双工另一方向；主机轮询/处理时间另算 |

当前串口只传方向、状态、序号、年龄和校验，不传七路音频。115200 8N1的有效字节上限为11,520B/s，远低于七路PCM16的672,000B/s；不能沿用该波特率转发原始音频给ESP32。

合并时同时保留采集时限：当前每块解包约1.824ms，块到达间隔10.667ms；其余任务不能长时间屏蔽DMA中断或延误块所有权交接。PIO状态机、DMA通道、GPIO与CPU期限都是资源，不能只核算串口负载。阵列数据线GP6–9、时钟GP10–11、LED预留GP12–13和UART GP0–1保留现有分配。

慢更新可能掩盖转向抖动，但不是解决控制冲突的依据。后续将感知更新与控制执行周期分离，结合真实反馈决定指令频率、速度/加速度限制；目前没有连接电机，尚未证明车轮控制稳定。
